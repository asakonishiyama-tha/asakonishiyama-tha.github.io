# Managing THA Talks

## 目的

社長の言葉から、縦に流れるTHA Web Talkを一緒に形にする。技術作業より先に「誰がどう変わり、何をするか」を決める。

**必須:** 作業前に `references/project-contract.md` を完全に読む。現在のREADME、`docs/launch-checklist.md`、対象Talk、schema、package scriptsを調べ、記憶よりリポジトリ事実を優先する。

## モードを宣言する

- **相談 / Conversation:** 対話と提案だけ。ファイルやGitを変更しない。
- **Add:** 公開許可済みPDF・写真を、解決済みTalkへ接続する。
- **Create:** 承認済み素材から新規Talkをローカル下書きで作る。公開リポジトリへ入れない。
- **Improve:** 実画面の最弱点と離脱点を示し、承認された範囲だけ直す。
- **Review-only:** 証拠付き評価だけ。編集、commit、push、公開はしない。

ユーザーの依頼が複数モードを含む場合も、現在のモードと次の承認を明示する。

## 社長との会話

リポジトリから分かることは質問しない。一度に1問だけ、未確定の次テーマを聞く。

1. **対象者** — 誰が、どんな場面で聞くか
2. **変化** — 聞く前と後で何が変わるか
3. **行動** — 終了後の成功行動を一つ
4. **根拠** — 使える事実、写真、PDF、体験談
5. **持ち帰り** — 後で使う資料・診断・行動資産

「社長らしく」を勝手な高級感や力強さに翻訳しない。本人の言葉を短く言い直して確認する。Createまたは大きなImproveでは、Trigger→Action→Variable Reward→Investment→Next Triggerが異なるA/Bの2案を示し、選択後に編集する。

## 作る体験

Hookedは参加者の利益のために使う。物語は問い→危機→反転→具体的根拠→本人の次の一歩。横スライドの模倣ではなく縦のリズムを作る。THA色、写真、動き、ゲーム性は意味を持たせ、動きを止めても理解できるようにする。

事実・仮説・Unknownを分ける。権利、出典、alt、個人情報、フォーム設定を推測しない。

## 完了の伝え方

社長向けには「狙う変化 / 今回決めたこと / 見る場所 / 確認結果 / 次に必要な承認」を先に伝える。技術詳細は必要時だけ後ろへ置く。

commit、push、Pages公開、GAS、Sheet、メール、Slackは別ゲートである。`docs/launch-checklist.md` の10個のうち、明示承認された次の1ゲートだけ実行する。
